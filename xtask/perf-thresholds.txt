# CI limits for `cargo xtask perf --check` (.github/workflows/perf.yml).
# How the gate works and how to change these: docs/perf-baseline.md, "CI gate".
#
# Columns: workload, size (full = the size the 1.0 target is stated for;
# quick = a tenth of it), the target in ms (the product claim on the
# reference machine, an Apple M4 Pro; reported, never gated: the 1.0 exit
# targets, plus the proposed-gate values for recalc_mix and
# incremental_10k), then the CI
# limit in ms per OS for the BEST of the runs (5 by default; 3 for
# recalc_mix and open_ods_50mb; 15 for incremental_10k and chart_10k).
# `123?` = not yet calibrated on that OS's GitHub-hosted runner (still
# gates); `-` = not gated on that OS.
#
# Uncalibrated limits are guesses: the M4 Pro's best (2026-11-13, busy
# machine) x an assumed runner slowdown (macos-15 2x, ubuntu-24.04 2.5x,
# windows-latest 3x; 3-4 cores instead of 12 for the parallel recalc)
# x 2 for noise and runner-to-runner variation, at least 10 ms.
# First CI run (2026-11-13): ubuntu-24.04 and windows-latest passed at
# 28-58 % of their limits. macos-15 (3 cores) was slower and noisier than
# assumed: recalc_chains best 82 ms / median 113 ms against 80 (4x the
# M4 Pro, not 2x), so the macOS guesses were raised to about 2 x that
# run's best. Still one sample: all limits stay provisional.
# Calibrate: limit = 1.75 x the slowest best-of-runs seen in at least
# three CI runs on that OS, rounded up, and drop the `?`.
# Calibrated 2026-11-16: ubuntu-24.04 from three CI runs (2026-11-13
# twice, 2026-11-16), windows-latest from four (the fourth ran on a
# runner about 25 % slower in every workload), macos-15 from three, with
# a floor of 10 ms for the two workloads that take about 5 ms.
# pdf_20p is provisional again on every OS: since 2026-11-16 default-size
# text prints at 11 pt, as on screen, not 10 pt, which takes the workload
# from 11 ms to 16 ms on the M4 Pro (one CI sample since: macOS 26 ms,
# Linux 31 ms, Windows 46 ms on the slow runner).
